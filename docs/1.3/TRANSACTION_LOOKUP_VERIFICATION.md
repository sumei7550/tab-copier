# 恢复查询与 PayPal 买家号验证

日期：2026-11-27。当前仅用于沙盒。此前恢复管理页只支持 `provider_capture_id`，不能把买家交易号查不到当成没有付款。

## 官方资料核查结果

- [PayPal 买家与卖家交易号说明](https://history.paypal.com/us/cshelp/article/why-are-there-different-buyer-and-seller-transaction-ids-for-the-same-transaction-ts2265)：同一笔支付有不同买家号和卖家号，卖家可在 PayPal 交易记录中搜索买家号。
- [Transaction Search API](https://developer.paypal.com/api/transaction-search/v1/search-get)：提供 `transaction_id` 过滤，要求 `reporting/search/read` 权限、起止时间，单次最大 31 天，交易报表可能延迟最多三小时。文档未承诺把买家号映射成卖家 capture，也不能将报表的任意 `paypal_reference_id` 当作买卖双方编号映射。

以上只验证了文档契约，没有证明当前账号支持买家号 REST 查询。本轮本地没有 Vercel 中的 PayPal 凭据，浏览器会话工具连接超时；没有对真实沙盒 API 作成功断言，也没有复制服务器密钥到本机。

## 已实现规则

1. 邮件模板保留当前安装参考编号，购买联系邮箱与 PayPal 付款邮箱分开填写，交易号如有可提供。参考编号定位目标安装，不能用于证明购买。
2. 交易号选填，提供时先精确匹配卖家 capture 或已核实保存的买家别名。没有或无法匹配时，按购买联系邮箱/已保存的 PayPal 付款邮箱精确查候选订单，每个邮箱最多 20 条；不做模糊匹配。管理员选择后由服务端核实付款，不需要再复制卖家号。
3. 未知交易号尝试 Transaction Search。只有返回与输入完全相同的交易号、正确商户账号、成功付款事件、正确金额和币种、明确的本地订单关联，才成为候选；随后仍用 Orders API 核实 capture。空结果、权限不足、不可用、多页或多候选均进入人工核查，不认定未付款。
4. 首次买家号不能自动验证关联时，管理员在卖家 PayPal 后台找到对应收款，填写卖家号并明确确认两个编号属于同一付款。最终签发前重新验证 PayPal、付款归属勾选和备注，再保存有审计备注的编号关联。此后买家号与卖家号都可直接匹配。
5. 按邮箱选中的订单不会把未验证的买家号自动存成别名。已精确匹配某个订单的交易号，不能借另一个邮箱选择不同订单。
6. 邮箱不决定授权。无论哪条路径都需要有效恢复请求、未撤销/未到期的授权、已完成且金额/币种/商户一致的收款，以及管理员确认归属。签发与兑换仍使用原有私密恢复流程。

## 两种邮箱

- `orders.purchase_email` 是购买前填写的联系邮箱，未做邮箱归属验证。
- `orders.paypal_payer_email` 从已核实的 PayPal Orders 响应 `payer.email_address` 取得。付款接口不会使用浏览器自报的 PayPal 邮箱写入该字段。缺失邮箱不阻止有效付款。
- 历史订单在管理员核查其交易时可回填 PayPal 返回的邮箱；尚未回填的历史订单无法通过缺失字段检索，需交易号或 PayPal 后台核对。不批量扫描所有 PayPal 交易。
- 两个邮箱仅用于业务核对，不发给 Mixpanel，不自动发邮件。

## 在 Vercel 上实际验证 API

1. 先执行 `website/supabase/migrations/005_transaction_aliases.sql`，再部署本次代码；不改已有密钥。
2. 管理页输入参考编号和用户的买家交易号，必要时填付款日期。若未自动匹配，进入人工核查区。
3. 从卖家 PayPal 后台核实该买家号对应的卖家收款号，填入，然后点「对比 PayPal 接口查询」。该操作只查询，不签发授权，也不建立别名。
4. 服务器先核实本地订单的真实 capture，再使用同一商户凭据、同一付款时间窗口，分别查询买家号与卖家号。结果只返回数量、是否精确匹配及订单关联，不返回访问令牌或付款人完整资料。
5. 结论区分：观察到买家号关联；卖家正对照成功而买家本次未匹配；缺少查询权限；结果不足以判断。若卖家正对照失败、报表未更新或接口异常，不能得出“不支持买家号”的结论。即使单次成功，也不承诺所有历史交易都可查询。

## 迁移与测试

005 新增已核实交易别名表、邮箱索引、PayPal 邮箱字段和服务端 capture 重载。别名 RLS 隔离，写入只通过 service-role RPC；已退款订单拒绝写入，同一编号不能被重绑或覆盖另一订单的卖家号。旧函数保留，以兼容历史调用。

本地测试覆盖直接/已存买家号、API 严格关联条件、权限/空结果/多页降级、人工关联确认、邮箱候选选择、已知交易冲突、邮箱分离、别名幂等与冲突/匿名权限，以及成对接口验证的正对照规则。真实账号权限和查询结果仍需上述 Vercel 验证。管理员 API 保留登录、Origin 与限流校验。

备注输入显示至少 8 字符及当前字数，避免按钮无解释地置灰。生成的恢复链接仍需购买者打开并点击「确认恢复」；随后插件才可用本地恢复请求秘密兑换，链接不需粘贴进插件。

## 插件恢复入口统一

删除容易与恢复混淆的公开「Check purchase」按钮，弹窗/设置页直接提供「恢复购买」。同一个动作检查已知本地付款、刷新现有授权、兑换已确认恢复请求，或准备人工恢复申请并显示邮件引导。Pro 已激活时隐藏这个入口，客服入口保留。调用正在执行时按钮显示「正在恢复」且禁止重复提交，worker 合并并发恢复请求。普通问题反馈仍不会自动创建恢复申请。

恢复链接页收到 `{confirmed:true}` 后切换为绿色成功标识和「恢复确认成功」，隐藏确认按钮与无效链接警告，显示回到同一浏览器打开 Tab Copier、点击恢复购买的三步引导。页面确认与插件领取授权明确区分，不宣称网页已让插件生效；提供可复制的返回步骤，并兼容旧版客服入口。
